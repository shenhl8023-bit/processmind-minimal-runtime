# ProcessMind Win7 本轮缺陷清单

更新日期：2026-10-26。修正包：`processmind-win7-windows-20261026-fix5.zip`，版本 `1.0.1+20261026-fix5`。fix4 已确认运行时打包错误，不再用于 Win7 验收。

## BUG-001：不存在的 API 和静态资源返回首页 HTML

- 状态：源码已修复并由回归测试覆盖；fix3 已完成 H01 开发机验证，fix4 还包含模型响应文本提取修复。Win7 实机复测尚未完成。
- 建议严重程度：P2，影响错误处理和异常诊断。目前没有证据表明它阻断已有的正常业务请求。
- 复现环境：macOS Python 3.13，使用新包内后端源码和生产前端，由同一 FastAPI 应用提供服务，使用独立临时数据库。
- 请求一：`GET /api/this-endpoint-does-not-exist`。
- 请求二：`GET /assets/this-chunk-does-not-exist.js`。
- 修复前：两个路径均为 HTTP 200，`Content-Type: text/html; charset=utf-8`，响应体与首页完全相同。每个请求重复两次，结果一致。
- 修复后：缺失 API 和资源返回 HTTP 404；缺失 API 即使声明 `Accept: text/html` 仍返回 404；带 `Accept: text/html` 的有效前端历史路由继续返回首页。
- 原因：`SPAStaticFiles.get_response` 对全部缺失 GET/HEAD 路径使用首页回退，没有区分页面导航、`/api/` 和静态资源路径。
- 代码位置：`process-plan-agent-api/app/web.py`，`SPAStaticFiles.get_response`。
- 可能影响：前端请求错误路径或丢失的静态资源时，真实的 404 被隐藏，可能表现为响应解析错误或脚本加载错误。
- 修复后的自动化验收：`process-plan-agent-api/tests/test_static_frontend.py` 检查 API、`/assets/`、缺失 JS 文件及无 HTML Accept 的路径均为 404，同时验证有效前端历史路由、已有静态资源和启动 API 正常。
- 尚未覆盖：Win7 实机上的真实浏览器 HTTP 请求。该项已列入 `docs/Win7功能测试方案-20261025.md` 的 H01/C01 验收。
- 修复前证据：`dist-win7/package-smoke-20261025.json`。

修复仅在收到 404 时判定是否能回退到首页：只有接受 HTML 的、无文件扩展名的前端历史路由使用 SPA 回退；`/api/`、`/assets/` 和文件型 URL 保留 404。Win7 业务验收中发现的新问题继续按编号追加，并记录包版本和操作步骤。

## BUG-002：合并后的工序再次拆分时被拆成工步

- 状态：开发机前端回归通过；Win7 实机 C06～C08 尚未执行。
- 复核结果：预览树按 `source_operation_ids` 找回原始工序，再按来源工序创建拆分项，不再把来源工序的 `step_items` 当成待拆分工序。
- 自动化覆盖：`useRouteMergeResultWorkspace.spec.ts` 验证单来源工序含多个工步时仍只有一道工序，以及两个来源工序合并后拆分能恢复各自名称和来源 ID。
- 仍需目标机确认：使用“车外圆B”与另一工序执行合并、拆分及连续重复操作，检查工步归属和保存/刷新后的状态。

## BUG-003：分组映射分次保存后仍提示缺少映射

- 状态：源码已修复并由回归测试覆盖；完整 Win7 六步业务验收尚未执行。
- 复核结果：先保存孔组、再补槽组时，第二次保存会合并保留已有映射；旧式 `/group-templates/mappings` 接口也会保留已经生成的全集路线快照，不再因为补保存分组而让后续规则包审查回到“没有映射/全集路线为空”。
- 自动化覆盖：`test_project_group_template_api.py`、`test_rule_package_lifecycle.py` 和 `TemplateGroupMappingDialog.spec.ts`，其中生命周期回归覆盖“分次保存 → 生成全集路线 → 再保存旧式分组映射 → 发布预检”。

## BUG-004：模型响应成功但模板映射提示“模型调用失败”

- 状态：源码已修复并由回归测试覆盖；已纳入 `processmind-win7-windows-20261025-fix4.zip`。Win7 实机及真实模型服务复测尚未完成。
- 原因：部分兼容模型在 HTTP 200 响应中把 `message.content` 返回为文本片段数组，或使用旧式 `choices[].text`；旧代码只读取字符串形式，解析失败后统一显示“模型调用失败”。
- 修复：统一兼容普通字符串、文本片段数组、旧式 `choices[].text`，并对成功但无文本的响应给出明确提示；异常日志只记录异常类型和 HTTP 状态码，不记录可能包含密钥的请求详情。
- 自动化覆盖：`tests/test_llm_client_config.py`、`tests/test_template_group_mapping.py`，以及分组映射端到端诊断用例。
- 仍需目标机确认：配置实际模型后执行分组模板映射和工步模板映射；分别验证文本字符串、片段数组和异常响应时的页面提示、人工候选保留与重试行为。

## BUG-005：Win7 无法读取进程命令行时停止脚本不释放 8000 端口

- 状态：源码已修复并由回归测试覆盖；已纳入 `processmind-win7-windows-20261025-fix4.zip`。Win7 实机 C02 仍需复测。
- 原因：旧停止逻辑只接受 WMIC 返回的完整命令行；部分 Win7 环境中 WMIC 不可用或返回空命令行，即使状态文件和健康检查都确认是本包服务，也会跳过 `taskkill`。
- 修复：当状态文件明确指向当前包、对应端口健康检查返回 ProcessMind 且命令行不可查询时，允许只终止状态文件记录的 PID；若命令行可查询仍执行包路径匹配，避免终止无关进程。
- 自动化覆盖：`tests/test_win7_launcher.py::test_stop_can_terminate_owned_healthy_service_when_wmic_has_no_commandline`，并保留无关命令行拒绝停止的回归测试。

## BUG-006：fix4 启动时缺少 api-ms-win-core-path-l1-1-0.dll

- 状态：用户在 Win7 虚拟机复现。运行时打包来源已修正，开发机静态校验及回归通过；fix5 在 Win7 虚拟机上的启动和业务复测待执行。
- 原因：fix4 的手动打包流程复制了开发用 `.runtime/python`，实际包含 Python 3.13 的 `python313.dll` 和 cp313 第三方扩展。PE 导入表确认 `python.exe` 导入 `python313.dll`，后者导入 Win7 缺失的 `api-ms-win-core-path-l1-1-0.dll`。第三方扩展还包含 Win7 不支持的 `bcryptprimitives.dll` 依赖，不能仅替换一个 DLL。
- 校验遗漏：fix4 的 manifest 和构建记录写成 Python 3.8.10 / 基线运行时未变化，但没有据实际文件生成和检查这些结论。先前“1967 个运行时文件一致”的记录不适用于 fix4；实际 fix4 有 2190 个运行时文件。
- 修复：fix5 整套恢复用户曾运行成功的 `processmind-win7-windows-20261023-win7fix2.zip` 中的 1967 个运行时文件。其五个核心 Python 文件与官方 `python-3.8.10-embed-amd64.zip` 的 SHA-256 一致，40 个依赖版本均与锁定清单一致。保留 fix4 的业务修复。
- 防回归：包校验器实际核对官方 Python 核心文件哈希、已安装依赖版本、必要兼容 DLL，并拒绝混入其他版本解释器或已知不兼容原生依赖；Windows 打包脚本压缩前必须通过该校验。9 个新增失败用例已完成先失败、修复后通过的验证。
- 交付要求：将 fix5 解压到新的空目录，避免覆盖解压残留 Python 3.13 文件；已有 KB2533623 无需因本次错误重复安装。此修复不修改 `%LOCALAPPDATA%\ProcessMind` 中的原有数据。
- 证据：`dist-win7/runtime-regression-20261026.json` 记录旧运行时通过、fix4 被拒绝；fix5 的逐文件比较、包内 SHA 和 ZIP 校验记录另存 `dist-win7/package-verification-20261026-fix5.json`。
