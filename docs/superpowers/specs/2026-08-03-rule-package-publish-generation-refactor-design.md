# 规则包发布与生成链路审查重构设计

## 背景

当前第 4 步负责把已确认规则编译并发布为不可变规则包，第 5 步读取当前已发布规则包并确定性生成工艺路线。近期代码已经把“发布”和“下载”拆成两个用户动作，但发布、读取和执行逻辑仍分散在大型路由与页面组件中。

基线验证结果：

- 后端：`237 passed, 1 skipped`。
- 前端：`107 passed`。
- 前端生产构建成功。

基线通过说明现有主流程可用，但不能覆盖并发期间规则包发生替换的情况。

## 已确认问题

### 1. 生成请求没有绑定用户看到的规则包

前端加载规则包的输入模式后，只提交 `project_id`、`expected_workflow_revision` 和 `factor_values`。后端在收到请求时重新读取当前已发布规则包。

发布新规则包不会递增工作流版本，因此可能发生以下时序：

1. 用户加载规则包 V1 的输入模式。
2. 另一请求发布规则包 V2。
3. 用户按 V1 的输入界面提交生成。
4. 后端静默使用 V2 执行。

结果可能是输入校验意外失败，也可能在输入字段兼容时生成用户没有审核过的 V2 结果。响应虽然包含实际规则包版本和哈希，但只能事后说明，不能阻止错误执行。

### 2. 最新规则包查询吞掉了所有错误

`FinalizeView` 和 `GenerateView` 都把最新规则包查询的任意失败转换成 `null`。因此 404、网络故障和服务端错误会被统一显示为“没有规则包”。在第 4 步，这还可能临时启用重复发布；在第 5 步，则会隐藏真实故障原因。

### 3. 发布与执行边界位于大型路由中

发布端的服务端校验、版本分配、持久化和生命周期切换集中在 `routers/extract.py`。V2 规则包加载、校验、输入验证和规划集中在 `routers/generate.py`。HTTP、事务、领域规则和响应组装交织，使异常语义难以单独测试，也增加后续修改时的回归范围。

## 目标

1. 生成必须使用前端加载并确认的同一规则包，或者在规则包过期时明确拒绝。
2. 只有 404 可以表示“没有已发布规则包”；其他错误必须保留真实语义。
3. 将发布和 V2 执行领域逻辑移出 HTTP 路由，使其可独立测试。
4. 保持正常发布、下载和生成流程的 API 路径、响应字段、界面文案与生成结果不变。
5. 保持 V1 历史调用兼容，并继续满足现有领域不变量。

## 非目标

- 不修改数据库结构或 ZIP 内容格式。
- 不改变只能下载当前 `published` 版本的规则。
- 不重写 V1 生成算法。
- 不修改规则编辑、标准因子目录或 KmAI 导出算法。
- 不调整页面布局、按钮文案或交互层级。
- 不顺带拆分与本链路无关的大型组件。

## 方案选择

采用“契约加固 + 定向拆分”。

未选择只做内联补丁，因为它会继续把并发校验和领域异常留在大型路由中。未选择全链路状态机和归档存储重构，因为该方案需要数据库迁移并扩大行为变化，不符合本轮保持外部行为的约束。

## 后端设计

### 发布服务

新增 `app/services/rule_packages/publishing.py`，承接发布领域逻辑：

- 校验请求中的 V1/V2 包结构和必填内容。
- 校验 `manifest`、项目、路线版本和已确认规则来源的一致性。
- 由服务端重新计算内容哈希、规则包校验结果和 KmAI 兼容结果。
- 分配项目内连续版本号。
- 创建新版本，并把此前的 `published` 版本切换为 `superseded`。
- 保留单项目仅一个 `published` 版本的数据库约束和冲突重试语义。

路由继续负责取得工作流写锁、提交或回滚事务、把领域异常映射为现有 HTTP 状态码，以及序列化响应。发布服务不自行开启跨请求事务，也不改变现有提交边界。

### 执行服务

新增 `app/services/rule_packages/execution.py`，承接已发布规则包执行逻辑：

- 加载项目当前 `published` 规则包，并在 V1/V2 分支之前根据请求中存在的预期指纹进行一致性校验。
- 解析和校验 V2 持久化内容。
- 校验实际提交的输入字段。
- 调用现有 `plan_route()` 确定性规划。
- 返回步骤、命中规则、选中工序和规则包元数据的类型化结果。

HTTP 路由继续负责项目工作流锁、V1/V2 分支选择、生成记录持久化、项目状态更新和 `GenerateResponse` 组装。V1 分支复用已经通过指纹校验的行，其生成算法保持原样。

### 请求契约

在 `GenerateRequest` 中增加三个可选字段：

- `expected_rule_package_id`
- `expected_rule_package_version`
- `expected_rule_package_hash`

新前端提交加载输入模式时取得的所有非空指纹字段。旧客户端不提交这些字段时，后端继续执行当前已发布规则包，以保持兼容。

当任一已提供字段与当前 `published` 包不一致时，执行服务产生“规则包已更新”领域冲突。路由映射为 409，且不得创建 `GeneratedRoute`、更新项目状态或执行规划。

## 前端设计

### 可选最新规则包读取

在 `src/api/extract.ts` 增加共享读取函数。它复用现有缓存与强制刷新参数，但只在响应状态为 404 时返回 `null`；网络错误、401、409、422 和 5xx 必须继续抛出。

`FinalizeView` 和 `GenerateView` 使用该函数替换各自的 `catch(() => null)`。这样“尚未发布”和“读取失败”保持不同状态。

### 生成上下文指纹

`GenerateView` 在加载输入模式时同时保存规则包的 ID、版本和内容哈希。生成时把这三个值传给 `generateRoute()`。

若后端返回规则包过期冲突，页面先清除旧生成结果并重新加载规则包上下文，再显示明确错误；刷新成功不能清除该错误。其他 409 仍沿用现有工作流过期处理语义。成功路径继续以响应中的实际规则包元数据展示和导出结果。

### 发布页面

`FinalizeView` 仍通过当前路线版本、规则确认状态和内容哈希判断已发布包是否为当前版本。仅改变最新规则包读取的错误分类，不改变按钮禁用条件、发布审核对话框或下载行为。

## 数据流

### 发布

1. 前端按当前规则卡片编译预览。
2. 用户在发布审核对话框确认。
3. 前端提交规则包和 `expected_workflow_revision`。
4. 路由取得项目工作流写锁。
5. 发布服务重新校验、计算服务端权威哈希并创建新版本。
6. 同一事务内替换旧 `published` 版本并提交。
7. 前端记录返回的当前版本，下载动作随即可用。

### 生成

1. 前端读取当前已发布包及其输入模式和指纹。
2. 用户填写输入，并连同指纹提交生成请求。
3. 路由取得项目工作流写锁。
4. 执行服务读取当前已发布包并比对指纹。
5. 指纹一致时才进行输入校验和 V2 确定性规划。
6. 路由持久化结果，响应继续返回实际规则包 ID、版本和哈希。
7. 指纹不一致时返回 409，前端刷新上下文，不产生生成记录。

## 错误语义

- 404：项目或已发布规则包不存在。
- 409：工作流版本过期、规则确认过期、发布冲突或生成请求的规则包指纹过期。
- 422：规则包结构、标准因子绑定、输入或规划无效。
- 5xx 与网络故障：保持原错误，不转换为“没有规则包”。
- 下载：继续把不存在映射为 404、非当前发布版本映射为 409、归档生成失败映射为 422。

规则包指纹冲突固定返回以下 409 `detail` 结构，以便前端只对该冲突自动刷新，避免把其他业务冲突误分类：

```json
{
  "code": "published_rule_package_changed",
  "message": "规则包已更新，请刷新后重新生成。",
  "current_rule_package": {
    "id": 123,
    "version": 4,
    "content_hash": "..."
  }
}
```

## 测试设计

### 后端

- 当前规则包的 ID、版本和哈希全部一致时，生成响应与现状完全一致。
- ID、版本或哈希任一不一致时返回 409。
- 指纹冲突不得调用规划器，不得创建生成记录，不得更新项目状态。
- 请求未提供指纹时保持旧客户端兼容。
- 发布服务继续保证项目内版本递增、只有一个 `published` 版本，并在异常时完整回滚。
- V1 已发布包和 V1 引擎路径保持现有测试结果。

### 前端

- 最新规则包读取对 404 返回 `null`。
- 最新规则包读取对网络错误和 5xx 重新抛出。
- 生成请求包含加载时的规则包 ID、版本和哈希。
- 规则包指纹冲突会刷新生成上下文，并且不会保留旧生成结果。
- 其他错误继续使用现有错误格式化逻辑。
