# 规则包发布与生成链路审查重构设计

## 背景

ProcessMind 第 4 步把已确认规则编译并发布为不可变规则包，第 5 步读取当前已发布规则包并确定性生成工艺路线。当前主流程已经可用，但审查发现两个会影响用户判断的实际问题：

1. 前端加载规则包 V1 的输入模式后只提交项目、工作流版本和因素值。后端收到请求时重新读取当前发布包。如果期间发布了 V2，生成请求可能静默使用 V2。
2. `FinalizeView` 和 `GenerateView` 把最新规则包查询的任意失败都转换为 `null`，导致网络故障和服务端错误被显示为“没有规则包”。

发布、读取和执行逻辑还集中在大型路由和页面组件中。HTTP 编排、事务、领域校验和结果转换交织，使上述边界难以独立验证。

## 目标

1. 新前端生成请求必须绑定加载输入模式时看到的同一规则包；规则包发生替换时明确拒绝执行。
2. 兼容旧客户端：未提交规则包指纹时，后端继续使用请求执行时的当前发布包。
3. 只有 404 表示“没有已发布规则包”；其他读取错误保留真实语义。
4. 将发布和 V2 执行的领域逻辑移出 HTTP 路由并提供聚焦测试。
5. 保持正常发布、下载、生成、V1 历史调用和 KmAI 兼容导出的外部行为不变。

## 非目标

- 不修改数据库结构或迁移数据。
- 不修改 ZIP 内容、KmAI V1 文件名、顶层结构或字段语义。
- 不重写 V1 生成算法。
- 不修改规则编辑、标准因子目录或 KmAI 导出算法。
- 不调整页面布局、按钮文案或交互层级。
- 不拆分与发布和生成链路无关的大型组件。
- 不把规则包指纹变成旧客户端的必填字段。

## 方案

采用“契约加固 + 定向拆分”。

仅做内联修复的改动量更小，但会继续把并发校验和领域异常留在大型路由中。完整生命周期重构需要数据库迁移和更大的协议变化，超出本轮问题所需范围。

## 后端边界

### 发布服务

新增 `app/services/rule_packages/publishing.py`，负责：

- 校验 V1/V2 请求内容和必填资产。
- 校验 V2 manifest、项目、路线版本和已确认规则来源的一致性。
- 重新计算服务端权威内容哈希、规则包校验结果和 KmAI 兼容结果。
- 分配项目内连续版本号并创建持久化记录。
- 调用现有 `lifecycle.publish_rule_package()` 完成发布状态切换。
- 保留现有版本冲突重试和单项目唯一发布版本约束。

`lifecycle.py` 继续作为底层状态转换模块，不复制发布状态逻辑。发布服务使用类型化结果和领域异常，不直接抛出 `HTTPException`，也不自行提交外层事务。

`routers/extract.py` 继续负责取得工作流写锁、最终提交或回滚、把领域异常映射为现有 HTTP 状态码，以及序列化响应。发布校验、哈希、版本和状态转换不再留在路由函数中。

### 执行服务

新增 `app/services/rule_packages/execution.py`，负责：

- 加载项目当前 `published` 规则包。
- 在 V1/V2 分支之前校验请求中已经提供的规则包指纹。
- 解析并校验 V2 持久化内容。
- 校验本次实际提交的输入字段。
- 调用现有 `plan_route()` 进行确定性规划。
- 返回步骤、命中规则、选中工序和规则包元数据的类型化结果。

服务使用领域异常表达“没有发布包”“发布包已变化”“持久化包无效”“输入无效”和“规划失败”。它不创建 `GeneratedRoute`，不更新项目状态，也不提交事务。

`routers/generate.py` 继续负责工作流锁、V1/V2 路径编排、生成记录持久化、项目状态更新和 `GenerateResponse` 组装。V1 算法保持原样，但复用已经加载并通过指纹校验的发布包。

## 请求契约

`GenerateRequest` 增加三个可选字段：

- `expected_rule_package_id: int | None`
- `expected_rule_package_version: int | None`
- `expected_rule_package_hash: str | None`

新前端提交加载输入模式时取得的全部非空指纹字段。后端按字段独立比较：只要请求提供了某个字段，该字段就必须与当前发布包一致。

三个字段均未提供时，不执行指纹一致性检查，继续使用当前发布包，以保持旧客户端兼容。

## 冲突响应

任一已提供指纹与当前发布包不一致时，后端在输入校验、规划和持久化之前返回 409：

```json
{
  "detail": {
    "code": "published_rule_package_changed",
    "message": "规则包已更新，请刷新后重新生成。",
    "current_rule_package": {
      "id": 123,
      "version": 4,
      "content_hash": "..."
    }
  }
}
```

稳定的 `code` 用于前端区分规则包变化和其他工作流冲突。不得仅依赖中文消息判断错误类型。

## 前端设计

### 可选最新规则包读取

在 `src/api/extract.ts` 增加共享读取函数。它复用现有缓存和强制刷新参数，但仅在响应状态为 404 时返回 `null`；网络错误、401、409、422 和 5xx 继续抛出。

`FinalizeView` 和 `GenerateView` 使用该函数替换最新规则包查询上的 `catch(() => null)`。这样“尚未发布”和“读取失败”保持为不同状态。

### 生成上下文指纹

`GenerateView` 加载输入模式时同时保存规则包 ID、版本和内容哈希，生成时把指纹与因素值一起提交。

生成成功后以响应中的规则包元数据作为本次结果的权威信息，不再需要用额外的最新包查询证明结果版本。

收到 `published_rule_package_changed` 时：

1. 清除旧生成结果和旧规则包上下文。
2. 强制重新读取当前发布包及输入模式。
3. 按新输入模式重新初始化表单，避免旧字段和值进入新规则包。
4. 保留明确的规则包过期提示，要求用户检查输入后重新生成。

其他 409 继续沿用现有工作流冲突处理和错误格式化语义。

## 数据流与事务

### 发布

1. 前端按当前规则卡片编译预览并提交发布请求。
2. 路由取得项目工作流写锁。
3. 发布服务重新校验内容并计算服务端权威哈希。
4. 发布服务创建新版本并调用生命周期服务切换发布状态。
5. 路由提交同一事务并返回当前发布包。
6. 任一阶段失败时回滚，不留下草稿或多个发布版本。

### 生成

1. 前端读取当前发布包、输入模式和指纹。
2. 用户提交因素值及加载时的规则包指纹。
3. 路由取得项目工作流写锁。
4. 执行服务读取当前发布包并比较已经提供的指纹。
5. 指纹一致时才进行 V2 解析、输入校验和规划；V1 路径复用同一已校验包。
6. 路由持久化结果并提交，响应返回实际使用的规则包元数据。
7. 指纹冲突时返回 409，不执行规划，不创建生成记录，不更新项目状态。

## 错误语义

- 404：项目或最新发布规则包不存在。
- 409：工作流版本过期、规则确认过期、发布冲突或生成请求的规则包指纹过期。
- 422：规则包结构、标准因子绑定、输入或规划无效。
- 网络故障和 5xx：保持原错误，不转换为“没有规则包”。
- 下载：继续把不存在映射为 404、非当前发布版本映射为 409、归档生成失败映射为 422。

服务层异常不依赖 FastAPI。路由是唯一的 HTTP 状态码映射边界。

## 测试设计

### 后端

- 当前规则包的 ID、版本和哈希一致时，生成响应和结果保持不变。
- ID、版本或哈希任一不一致时返回结构化 409。
- 只提交部分指纹时，只比较已经提交的字段。
- 三个指纹均未提交时保持旧客户端兼容。
- 指纹冲突不得调用规划器、创建生成记录或更新项目状态。
- 发布服务继续保证版本递增、单项目只有一个 `published` 版本，并在异常时完整回滚。
- V1 发布包和强制 V1 引擎路径保持现有行为。
- 下载归档和 KmAI 兼容导出继续通过既有测试。

### 前端

- 可选最新包读取对 404 返回 `null`。
- 可选最新包读取对网络错误和 5xx 重新抛出。
- 生成请求包含加载时的规则包 ID、版本和哈希。
- 规则包指纹冲突会清除旧结果、刷新输入模式并保留过期提示。
- 其他错误继续使用现有格式化逻辑。

不为测试引入新的前端依赖；优先使用现有 Vitest 模块模拟和可独立测试的纯函数边界。

### 回归验证

- 后端全量 `pytest`。
- 前端全量 Vitest。
- `vue-tsc` 和 Vite 生产构建。
- `git diff --check`。

## 完成标准

1. 已确认的并发时序不能再导致新前端静默跨版本生成。
2. 非 404 的最新规则包读取错误不再显示为“没有规则包”。
3. 发布和 V2 执行逻辑具有独立服务边界及聚焦测试。
4. 正常发布、下载、生成和旧客户端调用保持兼容。
5. 数据库结构和 ProcessMind/KmAI 交接协议保持不变。
6. 聚焦测试、全量测试、生产构建和差异检查均通过。
