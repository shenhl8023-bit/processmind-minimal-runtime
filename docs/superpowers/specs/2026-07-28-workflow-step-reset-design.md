# 第二至第四步重新处理与下游失效设计

## 目标

为第二至第四步建立一致、可追踪的重新处理机制，保证上游结果发生变化后，下游不能继续展示或使用旧答案、旧审核结果和旧规则包。同时为第三、第四步提供影响范围明确的主动重做入口。

“清空下游”不表示页面永久空白。系统可以基于最新上游结果重新生成基础路线、问题和规则候选，但不得恢复任何属于旧版本的用户决定。

## 当前问题

- 第二步“重新推理”先返回后台任务，再由后台异步删除旧数据，存在读取旧结果的时间窗口。
- 后端会删除路线版本、第三步问答审核和第四步条件审核，但不会使已发布规则包失效。
- 第三步浏览器存储被删除后，已经打开的页面仍可能保留内存中的问答状态。
- 第四步本地条件草稿没有随第二步重跑清除；稳定的工序 ID 会使旧草稿再次套到新路线。
- 第四步的刷新按钮只重新加载数据，不等于重新识别规则，用户无法从按钮名称判断其作用。

## 总体原则

1. 上游重算必须级联失效所有依赖该结果的下游用户决定。
2. 数据失效由后端作为最终事实来源，前端清理只用于立即更新界面。
3. 失效动作应在重算任务被接受时完成，不能等后台模型任务真正开始后再清理。
4. 历史规则包保留用于追溯，但状态改为 `archived`，不能继续驱动第五步。
5. 每一步只清理自身及下游，不反向删除已经确认的上游结果。
6. 重新识别和人工审核使用不同名称，避免把模型行为描述为用户行为。

## 操作与影响范围

### 第二步：重新推理

用户确认后，系统立即执行以下操作：

- 清除第二步旧归并快照和标准化路线版本。
- 清除第三步全部工序问答、补充说明和审核记录。
- 清除第四步条件草稿、候选 AST、确认 AST 和人工模式确认结果。
- 将当前已发布规则包归档，使第五步无法继续加载旧包。
- 清除或标记第五步旧生成结果为过期，避免被误认为由最新规则包生成。
- 清除对应项目的前端缓存、本地草稿和已挂载页面内存状态。

清理成功后才启动新的第二步后台任务。如果任务启动失败，下游仍保持失效状态，因为旧结果已经不再对应一次有效的当前推理。

确认提示应明确显示：“将重新生成路线，并清除第三步回答、第四步审核和当前规则包。历史规则包仍可在版本记录中查看，但不能继续用于生成。”

### 第三步：重新回答全部

在第三步页头增加次要按钮 `重新回答全部`。当前已有的 `重答最后一题` 和 `重新判断这道工序` 保持不变，用于局部修正。

全量重答执行以下操作：

- 保留第二步标准化路线。
- 清除第三步所有工序的答案、说明和审核记录。
- 清除第四步所有条件草稿、候选和确认结果。
- 归档当前已发布规则包，并使第五步旧结果过期。
- 回到第三步第一道待回答工序。

确认提示应明确显示受影响的数据数量，并说明第二步路线不会改变。

### 第四步：重新识别全部

在第四步页头增加次要按钮 `重新识别全部`。现有刷新图标仍只负责从服务器重新加载最新数据，提示文案保持为“刷新结果”。

重新识别执行以下操作：

- 保留第二步路线和第三步问答结论。
- 保留用户当前填写的条件原文，包括手工修改后的文本。
- 清除第四步的候选 AST、确认 AST、置信度、问题说明和确认信息。
- 将条件状态恢复为待识别，并批量重新调用当前解析流程。
- 归档当前已发布规则包，并使第五步旧结果过期。
- 人工设置的主工序和人工 Bool 条件视为用户明确决定，默认保留，不调用模型覆盖。

重新识别结束后，安全且无歧义的候选可以进入待审核状态；存在问题的规则继续显示为待处理，不能自动确认或导出。

## 后端边界

新增统一的项目工作流失效服务，按起始步骤执行事务化清理：

- `from_step=2`：失效第二步及全部下游。
- `from_step=3`：保留第二步，失效第三步及全部下游。
- `from_step=4`：保留第二、第三步，只重置第四步机器识别结果及下游规则包。

第二步启动接口必须在成功占用任务执行权后、返回任务已排队前调用失效服务。并发重复点击只能有一个请求获得执行权，不能重复启动后台任务。

第三步和第四步分别提供明确的重置接口。接口返回清理数量、归档规则包版本和新的工作流修订号，前端据此更新提示并清除对应缓存。

所有第四步保存、确认和导出请求继续校验 `route_version_id`。失效后携带旧路线版本的请求必须返回冲突错误，不能重新写回旧数据。

## 前端状态同步

- 后端重置成功后，提升项目级工作流修订号并清除该项目 API 缓存。
- 通过项目级重置事件通知已挂载的第三、第四步页面清空内存状态。
- 第二步重跑清除第三步问题树本地存储和第四步草稿本地存储。
- 第三步全量重答只保留路线相关缓存，清除第三、第四步本地状态。
- 第四步重新识别保留条件原文草稿，仅清除识别及确认状态。
- 页面重新激活时必须比较工作流修订号；修订号变化后强制从服务器重新加载。

## 状态与反馈

- 重置进行中时禁用重复点击和前往下游步骤的入口。
- 重置失败时显示具体失败阶段，不在前端假装已经清空。
- 第二步任务失败后，第三、第四、第五步仍保持不可用，直到第二步产生并保存新路线。
- 第四步批量重新识别允许部分成功，但未成功项必须保持待处理并阻止规则包导出。
- 历史规则包列表继续展示归档版本，并明确标记“已过期”。

## 测试

### 后端

- 第二步重新推理请求返回前，第三步记录、第四步记录和当前发布包已经失效。
- 第二步重跑失败后，旧规则包不能重新成为发布状态，也不能驱动第五步。
- 第三步全量重答保留标准路线，仅删除第三、第四步决定并归档规则包。
- 第四步重新识别保留第三步回答和条件原文，删除机器候选与确认结果。
- 第四步重新识别不覆盖人工主工序和人工 Bool 条件。
- 旧 `route_version_id` 的并发保存请求被拒绝。

### 前端

- 第二步重跑后，返回第三步看不到旧问答状态。
- 第二步重跑后，第四步旧本地草稿不会重新出现。
- 第三步 `重新回答全部` 的确认提示和实际影响范围一致。
- 第四步 `重新识别全部` 保留原文，并显示新的识别进度和结果。
- 刷新按钮只重新加载，不触发解析。
- 归档规则包不会在第五步被选为当前规则包。

## 验收标准

- 任一上游重做完成后，下游界面和后端状态一致，不出现旧答案或旧确认结果。
- 第五步只能使用基于当前有效第三、第四步结果导出的最新发布包。
- 用户可以分别重做全部第三步回答或全部第四步识别，不必返回第二步。
- 三个重新处理入口均明确告知保留项、清理项和对规则包的影响。
