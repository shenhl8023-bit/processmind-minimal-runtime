# 第四步标准因子单入口设计

## 状态

- 日期：2026-07-29
- 状态：已确认
- 决策：删除可配置的 KmAI 映射功能，将规则语义和标准因子确认统一收回第四步。

## 背景

当前流程在第四步确认业务规则后，还可能要求用户在导出弹窗或“系统模型配置 > KmAI 映射”中再次判断“来源值应该对应哪个目标因子”。这造成了两类问题：

- 用户需要对同一业务语义确认两次。
- 后续映射缺少原规则上下文，容易产生“孔精加工映射为中间通孔”一类语义错误。

此外，手工布尔因子会生成同优先级的 `true` include 和 `false` exclude 规则。两个条件天然互斥，但当前校验器只按“优先级 + 工序”聚合动作，因此会把合法规则误报为冲突。

## 目标

- 用户只在第四步完成一次规则语义和标准因子确认。
- 删除项目级、全局和导出时临时 KmAI 映射。
- 导出阶段只验证和转换，不再要求用户作新的语义判断。
- 未知或有歧义的概念必须回到第四步处理。
- 保留历史已发布规则包的不可变语义。
- 修复手工布尔规则的同优先级冲突误报。

## 非目标

- 不改变 KmAI 现有因子计算和路线执行语义。
- 不自动猜测无法唯一对应的业务概念。
- 不重写已经发布的历史规则包。
- 不把独立映射管理页简单搬入第四步。

## 核心决策

### 唯一用户入口

第四步是唯一允许确认规则语义和标准因子的入口。每个最终条件叶子必须满足以下一种形式：

1. 绑定到不可编辑的 ProcessMind 标准因子。
2. 使用第四步创建的项目手工布尔因子。

原始条件文字继续作为审核证据保存，但不再作为导出时临时映射的依据。

### 删除动态映射，保留固定适配

完全删除用户可配置的 KmAI 映射子系统，包括项目覆盖、全局覆盖、提升、停用、版本、事件和使用记录。

KmAI 导出器仍需保留不可编辑的固定适配目录，用于将 ProcessMind 标准因子转换为 KmAI 因子键。该目录是版本化代码资产，不是运行时配置，也不提供管理界面或写接口。

## 标准因子模型

### 标准因子定义

标准因子目录由现有条件字段注册表统一提供。每个标准因子定义至少包含：

```json
{
  "factor_id": "feature.center_hole_location",
  "label": "顶尖孔定位",
  "category": "精度要求",
  "source_field": "cad.features",
  "canonical_value": "顶尖孔",
  "allowed_operators": ["contains", "contains_any", "contains_all"],
  "kmai_factor_key": "uses_center_hole_location"
}
```

`factor_id` 是 ProcessMind 的稳定语义标识，不等同于 KmAI 因子键。`kmai_factor_key` 只由固定导出适配器使用。

### 条件持久化

标准条件叶子在现有 `field / op / value` 基础上增加 `factor_id`：

```json
{
  "field": "cad.features",
  "op": "contains",
  "value": "顶尖孔",
  "factor_id": "feature.center_hole_location"
}
```

编译时必须验证：

- `factor_id` 存在于当前标准目录。
- `field`、`value` 和操作符符合该标准因子的定义。
- 复合条件中的每个可导出叶子都独立完成绑定。

手工布尔因子不设置标准 `factor_id`，继续通过 `project_factor.manual_process_*` 字段和“用户直接设定”字段定义识别。

### 注册表接口

扩展现有 `/api/extract/finalized-rule-packages/condition-fields` 响应，使其同时返回版本化标准因子目录。第四步继续从同一注册表读取条件字段和标准因子，不新增独立 KmAI 映射接口。

## 第四步交互

### 单条规则

- 规则解析完成后，系统基于标准目录推荐因子。
- 规则卡显示因子中文名和分类，例如“顶尖孔定位 · 精度要求”。
- 技术键放在次要信息或提示中，不要求普通用户理解。
- 用户可以搜索并更换标准因子。
- 没有合适标准因子时，可在当前规则卡创建手工布尔因子。
- 用户确认规则时，同时确认标准因子；不存在第二次确认流程。

### 批量审核

- 只有高置信度且标准因子唯一明确的规则可以自动确认。
- 存在未知值、多个候选或复合条件未完整绑定时，必须单独处理。
- 条件原文、条件结构或关联工序发生变化后，原因子确认立即失效。
- 注册表版本变化且影响已选因子时，规则回到待确认状态。

### 手工布尔因子

- 第四步继续提供“创建手工布尔因子”。
- UI 明确提示该因子不能由 CAD 自动得出。
- 导出摘要提示 KmAI 运行时需要通过 `manual.factor_overrides` 提供 `true/false`。

## 编译与导出数据流

1. 第四步保存原始证据、规范条件树和标准因子绑定。
2. 前端构建规则包时保留每个条件叶子的 `factor_id`。
3. 后端编译器验证规则结构、注册表版本和标准因子绑定。
4. KmAI 导出器从固定目录读取 `kmai_factor_key` 并生成兼容文件。
5. 导出审核弹窗只显示“审核通过”或“审核未通过”。
6. 审核通过后才发布并下载规则包。

导出流程不读取数据库映射，不创建映射，也不接受项目或全局覆盖。

## 导出审核

删除 `mapping_required` 状态和全部映射编辑控件。审核状态收敛为：

- `ready`：规则结构和固定 KmAI 适配均通过，可以确认导出。
- `blocked`：存在未绑定、失效、结构冲突或不受支持的条件，必须返回第四步处理。

阻断详情需要包含工序名称、规则来源和具体问题，并支持定位到第四步对应规则卡。

## 手工布尔冲突修复

校验器继续拦截真正的同优先级 include/exclude 冲突，但对以下精确模式作互斥豁免：

- 两条规则属于同一来源工序和同一手工布尔字段。
- 条件分别为该字段 `eq true` 与 `eq false`。
- `true` 分支 include、`false` 分支 exclude 同一工序。
- 两条规则均为已确认用户规则，且没有额外可能同时命中的条件。

不符合全部条件的组合仍按冲突处理。规划器运行时只会命中一个分支，因此该豁免不改变路线决策语义。

## 删除范围

### 前端

- 删除设置抽屉中的 `KmAI 映射` 页签。
- 删除 `KmaiMappingManagerDialog` 及其编辑、筛选和操作工具。
- 删除 KmAI 映射 CRUD、批量创建、预览和提升 API 客户端。
- 删除导出审核弹窗中的映射表单、草稿和保存流程。
- 删除 `mapping_required` 类型、分支和相关测试。

### 后端

- 删除 `/api/kmai-factor-mappings` 路由及注册。
- 删除映射请求/响应契约和映射存储服务。
- 删除动态映射注册表加载、作用域优先级和映射使用记录逻辑。
- 编译、保存和兼容性测试统一使用固定标准因子目录。
- 将历史规则包兼容性测试所需的快照从规则包自身的 `validation_report_json` 读取。

### 数据库

删除表之前，执行一次事务内回填：对仍有 `kmai_factor_mapping_usages`、但
`validation_report_json.kmai_compatibility.mapping_snapshot` 缺失的已发布规则包，
将使用记录中的不可变快照写入规则包校验元数据。回填只补充历史适配元数据，
不得修改 manifest、条件、工序、规则、测试用例或内容哈希。全部相关规则包都能
从自身读取快照后，才允许按外键依赖顺序删除：

1. `kmai_factor_mapping_usages`
2. `kmai_factor_mapping_events`
3. `kmai_factor_mappings`

启动维护逻辑不再创建、重建或迁移这些表。删除是一次性且不可逆的；历史规则包内容本身不删除。
回填或校验失败时必须回滚事务并保留原表，不能以丢失历史语义为代价继续启动清理。

## 旧数据迁移

### 未发布规则

- 与固定标准目录完全一致的旧条件自动补充 `factor_id`，无需重复确认。
- 只有在字段、操作符和值能够唯一确定标准因子时才允许自动补充。
- 自定义值、多个候选和不完整复合条件标记为“需要重新确认”。
- 旧项目/全局映射不参与迁移，也不用于推断标准因子。

当前错误映射，例如“孔精加工 -> 中间通孔”，直接清除，不进入任何迁移结果。

### 已发布规则包

- 已发布规则包保持不可变。
- 数据库清理前，将仅存在于使用记录表中的发布快照补充到规则包校验元数据；该操作不改变规则包业务内容和内容哈希。
- 若包内 `validation_report_json` 含发布时适配快照，历史兼容性测试使用该快照。
- 更早且没有快照的规则包只允许使用当时已有的固定内置目录回放。
- 新规则包不再写入动态映射身份、版本或作用域信息。

## 错误处理

### 第四步

- 未选择标准因子：禁止确认，提示选择标准因子或创建手工因子。
- 推荐存在歧义：列出候选但不自动确认。
- 标准目录加载失败：禁止确认并允许重试。
- 条件与所选因子不一致：由后端拒绝保存，前端保留用户编辑内容。

### 导出

- 遗留未知条件：阻断并定位对应规则卡。
- 标准目录版本过期：提示刷新第四步并重新确认受影响规则。
- 固定目录缺少 KmAI 转换定义：作为系统错误阻断并记录明确代码。
- 手工因子缺少运行时值不阻断规则包导出，但必须在摘要和 README 中提示。

## 测试设计

### 后端

- 标准因子目录契约和版本测试。
- 条件叶子 `factor_id` 与字段、值、操作符一致性测试。
- 已知旧条件的安全自动补充测试。
- 歧义和未知旧条件必须重新确认测试。
- 编译和保存不再查询动态映射表测试。
- 固定目录生成 KmAI 因子条件测试。
- 历史规则包从自身快照回放测试。
- 手工布尔 `true/false` 规则通过校验并分别纳入/排除测试。
- 非互斥同优先级 include/exclude 仍失败测试。
- 数据库升级后映射表不存在且应用可启动测试。
- 原映射 API 不再注册测试。

### 前端

- 第四步显示推荐标准因子测试。
- 搜索、更换和确认标准因子测试。
- 未绑定和歧义规则不能批量确认测试。
- 条件变化使因子确认失效测试。
- 手工布尔因子创建和提示测试。
- 设置抽屉不再显示 KmAI 映射测试。
- 导出审核只存在 `ready/blocked` 测试。
- 阻断项定位到第四步规则卡测试。
- 删除映射 API 客户端和相关组件后的类型检查测试。

### 集成验收

- 用户从第四步到导出只进行一次语义确认。
- “孔精加工”不能配置为“中间通孔”。
- 四个手工开关不再产生虚假冲突。
- 未知值无法绕过第四步进入最终规则包。
- 已发布历史规则包仍能执行兼容性测试。
- 前端单元测试、类型检查、生产构建和后端完整测试通过。

## 完成标准

- 产品界面中不再出现项目映射、全局映射、提升为全局或导出时补映射入口。
- 代码中不存在动态 KmAI 映射 CRUD 和数据库依赖。
- 第四步能够完成标准因子建议、选择、确认和手工因子创建。
- 导出器只接受已确认的标准因子或手工布尔因子。
- 数据迁移、历史包回放和手工布尔冲突修复均有自动化覆盖。
