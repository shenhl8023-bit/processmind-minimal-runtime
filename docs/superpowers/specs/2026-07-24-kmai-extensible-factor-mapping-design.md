# KmAI 可扩展因素映射设计

## 目标

将 ProcessMind 到 KmAI v1 的因素映射从后端硬编码表升级为可配置、可审计、可分层复用的产品能力。

第一版应当满足以下结果：

- 用户在第四步导出规则包时，可以就地处理 `cad.features` 等字段的未映射值。
- 用户可以把一个 ProcessMind 值绑定到已有 KmAI 因素，也可以创建一个由 `manual.factor_overrides` 提供值的新布尔因素。
- 映射支持“系统内置、全局、项目”三层作用域，项目映射优先于全局映射，全局映射优先于系统内置映射。
- 已确认映射可以跨规则包导出复用，不需要每次修改代码或重复处理。
- 映射不明确时继续阻止导出，避免生成能够加载但语义错误的 KmAI 规则。

## 非目标

第一版不包含以下能力：

- 不提供 CAD 自动识别条件编辑器。
- 不允许用户配置 `canonical_feature`、`precision_rank`、`group_path` 等 KmAI CAD 过滤规则。
- 不自动推断两个业务术语是否等价。
- 不改变 ProcessMind V2 原生规则执行语义。
- 不移除当前系统内置 KmAI 因素和因素展开规则。

## 当前问题

ProcessMind 的条件字段允许自定义值。条件解析器遇到明确但未预列的结构特征时，会保留原始语义并生成类似以下条件：

```text
cad.features contains "孔类结构"
```

KmAI v1 导出器目前依赖静态 `_VALUE_FACTOR_MAP`，只有少量预定义值能够转换为 KmAI 因素。例如：

```text
cad.features contains "型孔/割扁"
    -> has_shaped_hole_or_cut_flat = true
```

当规则使用 `孔类结构`、`型孔`、`装夹定位中心孔` 等不在静态表中的值时，导出器无法确定目标因素，因此阻止导出。ProcessMind 的开放值策略与 KmAI 的封闭因素策略由此产生冲突。

## 方案选择

### 方案 A：继续扩充硬编码表

每次遇到新术语时修改 `_VALUE_FACTOR_MAP` 并重新发布后端。

优点是改动小；缺点是所有业务词汇都变成代码发布事项，不能支持项目差异，也没有 UI、审计和生命周期管理。因此不采用。

### 方案 B：仅允许绑定已有因素

将映射表配置化，但所有未映射值只能指向现有 KmAI 因素。

该方案可以解决同义词问题，却无法表达真正的新业务语义。用户可能为了通过导出而选择语义接近但并不等价的因素，造成隐蔽的路线错误。因此不单独采用。

### 方案 C：分层映射库，支持已有因素和人工因素

建立持久化映射库。未映射值既可以绑定已有因素，也可以创建人工输入型的新布尔因素。第四步提供就地处理入口，模型设置提供集中管理入口。

该方案能够覆盖同义词和新语义，同时把第一版范围控制在 KmAI 已有的 `manual.factor_overrides` 契约内。它是本设计采用的方案。

## 核心概念

### 映射来源值

映射来源由 `source_field` 和 `source_value` 唯一描述，例如：

```text
source_field = cad.features
source_value = 型孔
```

第一版对现有导出器已经特殊处理的选择类字段开放，包括：

- `cad.features`
- `precision.grades`
- `special.requirements`

以后增加字段时沿用同一模型，不新增另一套映射机制。

### 映射模式

`existing_factor` 表示绑定已有 KmAI 因素。它适合处理同义词或业务别名，例如：

```text
型孔 -> has_shaped_hole_or_cut_flat
```

`manual_factor` 表示创建新的布尔因素。导出的因素定义使用 `source_mode=manual_override`，默认值为 `false`，运行时必须通过 `manual.factor_overrides` 提供真实值。

### 作用域

`builtin` 是代码内随版本发布的系统映射，只读。

`global` 对所有项目生效，适合经过确认的标准术语和企业级别名。

`project` 只对指定项目生效，适合项目特有叫法、试运行映射和暂不适合推广的规则。

解析优先级固定为：

```text
项目映射 > 全局映射 > 系统内置映射
```

项目层可以覆盖全局或内置结果，但 UI 必须明确显示被覆盖的原映射。

## 数据模型

新增数据库表 `kmai_factor_mappings`，而不是把映射存入通用设置 JSON。映射需要查询、唯一约束、作用域、审计和引用保护，独立表更适合这些要求。

建议字段如下：

| 字段 | 含义 |
| --- | --- |
| `id` | 映射主键 |
| `scope` | `global` 或 `project`；内置映射仍由代码提供 |
| `project_id` | 项目映射必填，全局映射为空 |
| `source_field` | ProcessMind 条件字段 |
| `source_value` | ProcessMind 条件值，保存标准化后的精确文本 |
| `mapping_mode` | `existing_factor` 或 `manual_factor` |
| `target_factor_key` | KmAI 因素键 |
| `target_factor_name` | UI 和导出文件使用的因素名称 |
| `target_factor_category` | 已有因素类别或 `processmind_manual` |
| `status` | `active` 或 `inactive` |
| `revision` | 映射内容每次修改后递增的修订号 |
| `promoted_from_id` | 全局映射由项目映射提升时记录来源 |
| `created_by` / `updated_by` | 操作人 |
| `created_at` / `updated_at` | 审计时间 |

同一作用域内，`source_field + source_value` 必须唯一。项目映射的唯一键额外包含 `project_id`。

人工因素键必须符合 KmAI 因素键格式，建议统一生成：

```text
processmind_manual_<12 位稳定摘要>
```

摘要由字段和值生成，避免中文转拼音产生歧义，并确保同一来源值重复创建时得到相同建议键。用户可以查看因素键，但第一版不允许自由修改，以减少碰撞和兼容风险。

新增 `kmai_factor_mapping_events` 审计表。每次创建、修改、停用、重新启用、提升或删除映射时，记录操作类型、操作人、操作时间以及变更前后的 JSON 快照。`created_by` 和 `updated_by` 用于列表展示，事件表用于完整追溯。

新增 `kmai_factor_mapping_usages` 使用表。在规则包成功发布的同一事务中，为每条实际使用的映射写入：规则包 ID、映射 ID、映射修订号、来源字段和值、目标因素键、映射模式和作用域快照。系统内置映射没有数据库映射 ID，但仍记录稳定的内置映射标识和完整快照。

使用表承担两个职责：

- 解释历史规则包当时采用了哪条映射，不受后续修改影响。
- 在删除映射前提供可靠的引用检查，不依赖扫描自由格式 JSON。

## 后端架构

新增独立的映射服务，例如 `kmai_mapping_registry.py`，负责：

- 合并内置、全局和项目映射。
- 按优先级解析来源值。
- 校验映射冲突和目标因素合法性。
- 为人工因素生成稳定因素键和 KmAI 因素定义。
- 返回未映射值以及引用这些值的规则位置。

`kmai_export.py` 不再直接读取 `_VALUE_FACTOR_MAP`。它通过映射服务解析条件值，但系统内置映射可以继续以常量形式由映射服务加载，保证现有规则行为不变。

人工因素沿用现有动态因素导出结构：

```json
{
  "factor_key": "processmind_manual_<digest>",
  "name": "孔类结构",
  "category": "processmind_manual",
  "value_type": "boolean",
  "multiple": false,
  "required": false,
  "source_mode": "manual_override",
  "default_value": false,
  "description": "由 ProcessMind 映射创建；KmAI 需通过 manual.factor_overrides 提供 true/false。"
}
```

规则条件随后转换为：

```json
{
  "factor_key": "processmind_manual_<digest>",
  "op": "=",
  "value": true
}
```

## API 设计

新增映射管理 API，建议使用独立路由 `/api/kmai-factor-mappings`：

- `GET /catalog`：返回内置因素、动态人工因素和可绑定的目标因素列表。
- `GET /`：按项目、作用域、字段、状态和关键词查询映射。
- `POST /`：创建项目或全局映射。
- `PUT /{mapping_id}`：修改目标因素、名称或状态。
- `POST /{mapping_id}/promote`：把项目映射复制为全局映射。
- `DELETE /{mapping_id}`：仅删除未被规则包或其他映射引用的记录；其他情况要求停用。
- `POST /resolve-preview`：批量预检来源值，返回最终解析结果、覆盖关系和未映射项。

规则包编译或导出接口的 KmAI 兼容性结果增加结构化问题，不再只返回文本：

```json
{
  "code": "kmai_unmapped_value",
  "field": "cad.features",
  "value": "孔类结构",
  "occurrences": 3,
  "rule_refs": ["route_rules.rules[2]", "route_rules.rules[7]"],
  "suggested_existing_factors": [],
  "can_create_manual_factor": true
}
```

旧的文本错误仍可保留用于日志和向后兼容，但 UI 必须使用结构化数据渲染处理界面。

成功发布的规则包还应在 `validation_report_json` 中保存便于离线排查的有效映射快照。数据库使用表是引用关系的权威来源，包内快照用于下载 ZIP 后解释导出结果。

## 第四步导出流程

用户点击“审核并导出规则包”后，流程如下：

1. 编译 ProcessMind V2 规则包。
2. 收集 KmAI 需要解析的所有字段和值。
3. 按“项目、全局、内置”顺序解析映射。
4. 如果全部解析成功，继续现有兼容性校验和 ZIP 导出。
5. 如果存在未映射值，打开可处理的映射弹窗，而不是仅显示错误文本。
6. 用户逐项选择“绑定已有因素”或“创建人工因素”，并选择保存为项目映射或全局映射。
7. 后端原子化保存本批映射，再重新执行完整预检。
8. 预检通过后，用户点击“继续导出”；系统不在保存映射后静默下载文件。

弹窗按 `field + value` 聚合重复问题。例如 `孔类结构` 被三条规则引用时只处理一次，同时显示“影响 3 条规则”和可展开的规则位置。

对于人工因素，弹窗必须展示醒目说明：

```text
该因素不会从 CAD 自动得出。KmAI 运行时必须通过
manual.factor_overrides 提供 true/false；未提供时默认为 false，相关规则不会触发。
```

## 映射管理界面

在“模型设置”中新增“KmAI 映射管理”页，包含：

- 来源字段和来源值。
- 当前目标因素及映射模式。
- 作用范围：系统、全局、项目。
- 状态和最近修改信息。
- 被覆盖状态及最终生效映射。
- 搜索、字段筛选、作用域筛选和状态筛选。

系统内置映射只读。项目映射可以提升为全局映射，但提升操作必须显示可能与现有全局映射冲突的项目列表，并要求确认。

第一版不提供批量自动接受推荐。可以提供候选因素排序，但用户必须明确选择并保存。

## 校验与错误处理

创建或修改映射时执行以下校验：

- 来源字段必须在允许映射的字段集合中。
- 来源值去除首尾空白后不能为空。
- 已有因素必须存在于当前 KmAI 因素目录。
- 人工因素只能创建布尔类型，且因素键不得与内置或其他动态因素冲突。
- 同一作用域内的同一来源值不得重复。
- 全局映射冲突时拒绝提升，不允许覆盖式静默保存。
- 停用映射后，如果没有更低优先级的有效映射，后续导出重新报告未映射错误。

删除映射前通过 `kmai_factor_mapping_usages` 检查是否已经被已发布规则包引用。由于已发布 ZIP 包内包含完整因素定义，删除不会修改历史包，但 UI 应提示哪些历史版本使用过该映射。被引用的映射禁止物理删除，只允许停用；从未被引用的映射才允许删除。

## 当前三个问题值的处理建议

`型孔`可以作为项目映射绑定到已有 `has_shaped_hole_or_cut_flat`，前提是业务确认它与“型孔/割扁”的执行语义一致。确认稳定后可提升为全局映射。

`装夹定位中心孔`可以候选绑定 `uses_center_hole_location`，但不能由系统自动确认，因为“装夹定位中心孔”和当前内置“顶尖孔/中心孔定位”的业务范围可能不同。

`孔类结构`语义过宽，不应为了通过导出而绑定到“普通孔/辅助孔”或“铰孔/精孔”。第一版可创建人工因素，也可以要求用户回到规则定稿把条件细化为更明确的特征。使用人工因素时，导出包必须包含运行时传值说明。

## 兼容性与迁移

现有 `_VALUE_FACTOR_MAP` 条目作为 `builtin` 映射加载，不做数据库迁移，确保升级后现有规则的导出结果不变。

现有特殊要求动态因素逻辑应迁移到统一映射服务，但第一阶段可以保留兼容适配层。最终所有选择类字段都通过同一解析接口生成已有因素或人工因素。

历史已发布规则包保持不可变。新增、修改或停用映射只影响之后编译和导出的规则包版本。

数据库升级使用现有启动期 schema maintenance 机制创建表和索引，同时保证重复启动幂等。

## 测试策略

后端单元测试覆盖：

- 内置、全局、项目三层优先级。
- 项目映射覆盖全局映射。
- 已有因素映射的导出结果与当前结果一致。
- 人工因素生成稳定键、因素定义和布尔条件。
- 重复值聚合及规则引用位置。
- 冲突、停用、删除保护和全局提升。
- 映射修订递增、事件审计和发布时使用快照。
- 数据库升级的幂等性。

API 测试覆盖映射 CRUD、筛选、预检、提升和错误响应。

前端测试覆盖：

- 导出发现未映射值时打开处理弹窗。
- 重复错误按字段和值聚合。
- 两种映射模式的表单和警告。
- 保存后重新预检，未全部解决时不允许继续导出。
- 映射管理页的作用域、覆盖状态和停用操作。

端到端验收至少包含：

1. 把 `型孔`绑定已有因素后成功导出。
2. 把 `孔类结构`创建为人工因素后成功导出，并在 ZIP 中验证因素定义和使用说明。
3. 同一个全局映射在第二个项目中自动复用。
4. 项目映射覆盖全局映射，但不影响其他项目。
5. 停用唯一有效映射后，导出重新被兼容性检查阻止。

## 发布策略

第一阶段先发布后端映射服务、数据库表、结构化兼容性错误和测试，保留现有错误弹窗作为兼容回退。

第二阶段发布第四步就地处理弹窗和模型设置中的映射管理页。只有当前端能够完整处理结构化问题后，才移除只读文本弹窗的主要入口。

第三阶段根据真实使用情况决定是否增加 CAD 自动识别条件编辑器。该能力需要单独设计 KmAI CAD 过滤规则的验证、测试和权限，不属于本设计的第一版范围。

## 成功标准

- 新业务术语不再要求修改后端硬编码表。
- 用户可以在第四步内完成未映射值处理并重新导出。
- 全局映射可以跨项目复用，项目映射不会污染其他项目。
- 人工因素在 UI、导出包和运行说明中都明确标注其运行时输入要求。
- 不明确的语义仍然阻止导出，不发生静默猜测或错误绑定。
- 升级前能够导出的规则包在升级后保持相同 KmAI 执行语义。
