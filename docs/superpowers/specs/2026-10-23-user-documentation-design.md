# ProcessMind 用户文档设计

## 意图

为 ProcessMind 当前最小可运行包提供一套面向实际使用者的中文文档，说明系统解决的问题、完整工作流、每个页面的操作方式、输入输出、前置条件和常见故障。文档必须以当前仓库中的页面、接口和启动脚本为准，方便首次使用者从启动系统走到路线生成，也方便审核人员理解哪些结果需要人工确认。

## 目标

- 提供一篇短的《系统简介》，让首次接触者在几分钟内理解系统定位、核心概念、六步工作流和主要边界。
- 提供一篇可照着执行的《用户使用说明》，覆盖本地启动、Docker、Windows 7 交付入口、模型配置、项目和资料管理、六步业务流程、知识库查询、结果导出、重跑和故障排查。
- 在根 README 中增加文档入口，避免用户必须浏览源码才能找到说明。
- 明确主资料与参考资料的区别、草稿与已发布规则包的区别，以及 AI 建议和人工审核的责任边界。

## 非目标

- 不新增或修改产品功能、界面、API 和部署脚本。
- 不把仅存在于历史设计稿、旧试用记录或未注册路由中的功能写成当前可用功能。
- 不替代领域知识、工艺规程、质量体系或安全规范的人工审查。
- 不在文档中暴露真实 API Key、数据库内容、上传样例中的敏感信息。

## 约束

- 使用中文 Markdown，路径放在 `docs/`，并保留代码库已有的命名与 UI 文案。
- 运行方式以 `README.md` 当前描述为准：本地开发、Docker、Windows 7 离线包分别说明适用场景和入口。
- 功能描述需覆盖当前路由 `/upload`、`/extract`、`/analysis`、`/template-mapping`、`/finalize`、`/generate`、`/knowledge`，以及顶部“模型设置”。
- 文档只能声称当前代码已实现且可从界面触发的行为；对依赖模型、外部检索或模板文件的行为写清前置条件和失败表现。

## 方案与取舍

### 方案 A：单篇完整手册

把简介、安装启动和所有操作集中到一个文件。维护入口少，但首次阅读负担大，系统概览和操作细节难以分别引用。

### 方案 B：简介与使用说明分层（采用）

创建 `docs/系统简介.md` 和 `docs/用户使用说明.md`，README 链接到两篇文档；简介只保留定位与流程，使用说明承担可执行步骤、排障和边界。两篇文档共享同一套术语，后续可以独立更新。

### 方案 C：再拆出部署运维手册

将部署单独拆为第三篇。当前系统规模和交付方式还不足以支撑额外入口，容易让普通用户在多篇文档之间跳转；部署内容先放在使用说明的附录，待部署场景稳定后再拆分。

## 内容结构

《系统简介》包含定位、适用人员、核心概念、六步流程、辅助入口、典型产物和使用边界。

《用户使用说明》包含准备工作与启动、首次配置、项目和文件、六步操作、知识库、规则版本和重跑、导出与数据目录、常见问题、交付与安全注意事项。

README 在“运行方式”前后增加“用户文档”入口，并保持现有开发者与部署说明不变。

## 实施裁定

- 以当前 UI 文案作为用户可见名称，例如“路线归并”“模板分组映射”“规则定稿”“规则包验证与路线生成”。
- 将顶部“工艺知识库”作为独立辅助功能说明；不扩写为当前路由未提供的知识包管理后台。
- 将第 4 步称为“模板映射”，将规则包发布说明放在第 5 步；不把文档中的历史“第 4 步导出”表述照搬到当前 UI。
- 对模型未配置、没有已发布规则包、模板校验失败、规则包过期和没有可分析路线等状态分别给出处理动作。
