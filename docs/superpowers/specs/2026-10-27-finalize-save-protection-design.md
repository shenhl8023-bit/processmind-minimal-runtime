# 规则定稿保存与发布保护

用户在 2026-10-27 选定此前“保持清爽样式”的首轮方案并要求实施。

## 范围与约束

- 沿用现有布局、配色、字体、间距、规则卡片及提示组件。
- 复用标签显示“未保存”“有未发布修改”；已确认仅指当前保存的内容。
- 卡片内结构化修改、人工选择名称修改、原文编辑均纳入未保存检测。发布遇到未保存或正在保存的内容，停止并定位卡片。
- 原文保存先持久化到服务端，再尝试识别。识别失败保留原文；保存失败不能被说成保存成功。
- 摘要根据当前结构化规则生成，原文保留在现有依据折叠区。未保存编辑明确标记为未保存。
- 当前同源且通过校验的人工确认在重复识别、模型变化、第三步草稿复用及后台解析回写时受到保护。原文改变仍失效旧确认。
- 发布校验同时检查当前路线未确认规则及被请求遗漏的人工确认来源，保持已发布快照不可变。
- 本轮不做规则类型切换、试算或工序关联编辑器重新设计，不新增结构化草稿 API。

## 已选方式与替代方案

采用局部状态修复及现有服务端接口：文字草稿使用已有 draft 接口，结构化编辑继续“保存并确认”，未保存部分交给父页面拦截。统一重做编辑器与新增自动保存机制会扩大交互变化，留待后续。

## 实现边界

组件报告未保存状态；父页面管理发布拦截、持久化和状态文案；后端保护同源确认并验证发布来源。保留 API 合同和现有已发布版本语义。项目已有其他未提交修改，仅增量修改，不重置或批量提交。

## 验收

修改后旧“已确认”提示不再覆盖未保存状态；取消恢复原规则；发布能定位未保存项；识别失败后刷新仍能读回已保存原文；重复识别保留人工确认；后台解析不覆盖新确认；遗漏或未确认来源不能发布；已有页面样式与现有测试保持兼容。
