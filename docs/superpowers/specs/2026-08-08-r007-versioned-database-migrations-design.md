# R-007 启动期数据库维护改为版本化迁移设计

> - 日期：2026-08-08
> - 状态：已实施，验证通过
> - 跟踪条目：`R-007`
> - 影响范围：SQLite 启动迁移、数据库维护命令、升级与恢复文档、后端测试

## 1. 背景与根因

当前 `db_schema_maintenance.ensure_project_schema()` 同时承担以下职责：

1. 创建历史兼容表并补齐列。
2. 回填项目、工序链和规则包字段。
3. 创建或调整索引。
4. 规范化历史发布包并补齐内容哈希。
5. 迁移并删除历史 KmAI 映射表。
6. 在每次启动时审计重复工序。

`schema_migrations` 目前只记录 `retire_kmai_factor_mappings_v1`，没有统一的版本、顺序和执行结果约束。因此，大部分 DDL、扫描和回填在每次启动时重复执行；发生错误时只能看到底层 SQL 或数据异常，无法稳定定位到具体迁移。

根因不是缺少一条启动标记，而是结构升级、一次性数据迁移、持续审计和人工修复没有独立的执行边界。

## 2. 目标

1. 把启动期结构升级和一次性数据修复改为显式、有序、只执行一次的迁移。
2. 为每项成功迁移记录版本、名称、应用时间和结构化结果。
3. 在迁移失败时回滚启动事务，并报告失败迁移的版本和名称。
4. 兼容全新数据库、当前数据库和至少一个历史数据库快照。
5. 重复启动只读取迁移历史，不重复执行列补齐、回填、索引维护、发布包规范化或 KmAI 历史清理。
6. 将重复工序审计和合并修复移至显式维护命令。
7. 修复命令在写入前创建一致性备份，并提供可执行的恢复说明。

## 3. 非目标

- 不引入 Alembic 或其他运行时依赖。
- 不在 R-007 中支持 PostgreSQL 或其他数据库；SQLite 支持边界仍由 R-008 处理。
- 不改变 ORM 模型、业务 API、前端行为、V2 规则包、KmAI V1 四个 JSON 或 ZIP 结构。
- 不自动删除重复工序或重复因素。
- 不把持续数据健康检查重新放回应用启动路径。
- 不迁移或清理真实工作区数据库作为开发验证步骤。
- 不改造现有 `cleanup_duplicate_route_versions.py` 的路线版本修复语义。

## 4. 方案比较与决策

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| 仓库内置有序迁移注册表 | 无新依赖；适配现有异步 SQLAlchemy 与 SQLite；可精确保持历史兼容逻辑 | 需要自行维护迁移不可变约束 | 采用 |
| 引入 Alembic | 工具成熟；迁移生态完整 | 增加依赖、配置、离线交付和现有 `create_all` 整合成本 | 不采用 |
| 给现有单体函数增加一个总标记 | 改动最少 | 无法定位单项失败；不能独立兼容已有 KmAI 标记；审计和修复仍混在启动中 | 不采用 |

采用内置注册表后，迁移版本一旦发布只能新增，不能改写、重排或复用。

## 5. 模块边界

### 5.1 `db_schema_migrations.py`

新增迁移模块，负责：

- 迁移元数据类型与有序注册表。
- `schema_migrations` 控制表的兼容初始化。
- 已应用历史校验、待执行迁移筛选和顺序执行。
- 当前启动所需的结构迁移与一次性数据迁移。
- 将底层异常包装为包含版本和名称的迁移异常。

迁移模块不提供人工数据修复命令，不自行提交或回滚连接事务。

### 5.2 `db_schema_maintenance.py`

现有文件缩减为显式维护服务，保留：

- 重复工序扫描。
- 重复工序合并和因素重挂接。
- 修复后的唯一索引升级与结果验证。

这些函数只能由维护命令或聚焦测试调用，正常启动不调用。

### 5.3 `scripts/maintain_database.py`

新增标准库 `argparse` 命令，提供：

```text
python scripts/maintain_database.py --db <path> audit
python scripts/maintain_database.py --db <path> repair-operation-duplicates
python scripts/maintain_database.py --db <path> repair-operation-duplicates --apply
```

- `audit` 只读输出迁移历史、重复工序组和相关索引状态。
- 未带 `--apply` 的修复命令只输出将保留、合并和删除的行，不写数据库。
- 带 `--apply` 时先使用 SQLite 在线备份 API 创建同目录时间戳备份，再在事务中修复、验证并提交。
- 任何验证失败都回滚修复事务，保留备份并返回非零退出码。

## 6. 迁移控制表

新库使用以下逻辑结构：

```sql
CREATE TABLE IF NOT EXISTS schema_migrations (
    name VARCHAR(100) PRIMARY KEY,
    version INTEGER NOT NULL,
    applied_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    result_json TEXT NOT NULL
);

CREATE UNIQUE INDEX IF NOT EXISTS uq_schema_migrations_version
ON schema_migrations (version);
```

历史库可能只有 `name` 和 `applied_at`。控制表初始化属于迁移运行器的引导步骤，并与待执行迁移处于同一个外层启动事务：

1. 控制表不存在时创建完整结构。
2. 控制表存在时幂等补齐 `version` 和 `result_json`。
3. 将已有 `retire_kmai_factor_mappings_v1` 映射到其固定版本，并写入 `{"status":"adopted_legacy_record"}`。
4. 校验名称、版本唯一性以及已知名称与固定版本的对应关系。
5. 存在未知记录、空版本、重复版本或名称/版本漂移时拒绝启动，不猜测或覆盖历史。

每个新迁移仅在主体成功后插入记录。成功结果至少包含 `status="applied"`，有可计数结果的迁移同时记录修改行数或分支结果。失败迁移不留下成功记录；外层事务回滚后，通过 `DatabaseMigrationError` 和日志报告版本、名称与原始错误。

## 7. 初始迁移序列

现有启动逻辑按依赖关系冻结为以下版本：

| 版本 | 名称 | 职责 |
| --- | --- | --- |
| 1 | `legacy_project_schema_v1` | 创建历史兼容 `projects` 表；补齐项目关联列、`operations.chain` 和文档工序设备列 |
| 2 | `workflow_review_schema_v1` | 补齐条件审核列、项目模式/配置/引擎/工作流版本；创建提取任务状态和项目 ID 序列表；执行一次性项目与工序链回填 |
| 3 | `route_review_indexes_v1` | 创建路线、审核、参数答案和文档工序索引；根据历史重复工序状态建立唯一或普通工序身份索引 |
| 4 | `rule_package_lifecycle_v2` | 创建或升级规则包表；一次性迁移状态、补齐内容哈希、规范化每项目活动包并建立生命周期索引 |
| 5 | `retire_kmai_factor_mappings_v1` | 校验历史映射快照、回填不可变规则包报告、复核后删除三张退役映射表 |

迁移函数继续使用保护性 `CREATE ... IF NOT EXISTS`、列存在检查和限定条件回填，使其同时适用于：

- `Base.metadata.create_all()` 已创建当前结构的全新库。
- 缺少部分列或索引的历史库。
- 已执行 KmAI 退役迁移、但尚未记录其他版本的当前库。

工序身份索引迁移在无重复数据时创建唯一索引；存在历史重复时只创建普通索引，并在结果中记录重复组数量。应用启动不会自动合并历史业务数据。维护命令修复成功后负责把普通索引升级为唯一索引。

## 8. 启动与事务语义

`database.init_db()` 保持单一启动事务：

1. 设置 SQLite PRAGMA。
2. 调用 `Base.metadata.create_all()` 创建当前模型中不存在的表。
3. 调用 `run_schema_migrations(conn)`。
4. 由现有 `engine.begin()` 在全部成功后统一提交。

迁移运行器按版本升序执行所有待处理迁移。同一次启动中任一迁移失败时，当前事务中的建表、增列、回填、索引变更和迁移记录全部回滚。异常信息采用稳定格式：

```text
Database migration 4 (rule_package_lifecycle_v2) failed: <cause>
```

运行器不捕获后继续执行后续迁移，也不自动跳过失败数据。

为减少内部调用迁移成本，可保留 `ensure_project_schema(conn)` 作为调用 `run_schema_migrations(conn)` 的兼容薄包装；生产启动和新增测试统一使用新名称。

## 9. 显式维护与恢复

### 9.1 审计

审计命令至少输出：

- 当前数据库绝对路径。
- 已应用迁移的版本、名称、时间和结果。
- 未应用的代码内迁移列表。
- 重复工序组数量、每组项目/序号/名称和行 ID。
- `idx_operations_project_seq_name` 与 `uq_operations_project_seq_name` 的存在状态。

审计不调用迁移，不修改 `schema_maintenance_audit`，也不写业务表。

### 9.2 修复

重复工序修复沿用当前保守语义：

1. 每组保留 ID 最小的工序。
2. 将被合并工序的因素重挂到保留工序。
3. 仅删除完全相同的重复因素。
4. 删除被合并工序。
5. 重新审计，确认没有重复工序组或悬空因素。
6. 删除普通身份索引并创建唯一身份索引。

预览和实际执行必须使用同一份扫描结果结构，避免两个分支采用不同判定规则。

### 9.3 备份与恢复

写入命令使用源数据库连接的 `backup()` API 生成：

```text
<database-name>.bak-YYYYMMDDTHHMMSSZ
```

维护文档明确要求：

1. 执行前停止 ProcessMind API，避免审计与修复期间继续产生业务写入。
2. 先运行只读审计和修复预览。
3. 使用 `--apply` 后记录命令输出中的备份绝对路径。
4. 恢复时保持 API 停止，将失败数据库另行保留，再用备份覆盖原路径。
5. 重启后先运行迁移审计和 API 健康检查。

命令不得自动覆盖已有备份或在失败时自动删除原数据库。

## 10. 测试设计

### 10.1 迁移运行器

1. 全新数据库应用版本 1 至 5，历史表包含唯一且有序的成功记录。
2. 第二次启动不再次执行任何迁移函数，也不改写 `applied_at` 或 `result_json`。
3. 历史两列控制表能够升级，并正确接纳已有 KmAI 退役记录。
4. 未知迁移名称、重复版本和已知名称/版本不匹配时拒绝启动。
5. 测试迁移先产生 DDL/DML 后抛错时，主体变更和迁移记录均回滚，异常包含版本和名称。

### 10.2 历史库升级

1. 使用测试代码生成旧字段集合与退役 KmAI 表，再复制成独立 `.db` 快照后升级。
2. 升级后规则包业务字段保持不变，缺失映射快照按历史使用记录回填，退役表删除。
3. 非法 JSON、孤儿包引用、部分存在的退役表和回填验证不一致继续整体回滚。
4. 已有重复工序、因素和人工 `chain` 不被启动迁移删除或覆盖。
5. 历史规则包状态、哈希和每项目唯一活动包保持现有回归语义。

### 10.3 维护命令

1. `audit` 和无 `--apply` 的修复预览不改变数据库文件中的业务数据。
2. `--apply` 在任何写入前创建可打开的备份。
3. 修复后因素完整重挂、完全重复因素去重、重复工序清零且唯一索引存在。
4. 人工指定的非空工序链保持不变。
5. 注入验证失败时业务写入回滚，备份仍存在，命令返回非零。
6. 从备份恢复后数据库内容与修复前一致。

### 10.4 回归范围

- `test_db_startup_safety.py` 和新增维护命令测试。
- 规则包生命周期、API、状态、KmAI 导出与生成聚焦测试。
- 后端全量 pytest。
- `git diff --check` 与工作区状态核对。

R-007 不修改前端，因此不要求前端测试和构建作为完成门；若实施过程中实际改动前端，则必须补做前端全量验证。

## 12. 兼容性与风险

### 12.1 兼容性

- 保留 `Base.metadata.create_all()`，全新库初始化路径不变。
- 历史 `schema_migrations(name, applied_at)` 原地升级，不删除已有记录。
- `retire_kmai_factor_mappings_v1` 名称和既有安全校验保持不变。
- 不修改业务表字段语义、业务 API 或前端 DTO。
- V2 规则包、KmAI V1 文件、内容哈希算法和发布生命周期保持不变。

### 12.2 风险与控制

- **历史库形态多样：** 所有迁移保持幂等，并用全新库、当前形态和复制的历史快照覆盖。
- **迁移代码被后续改写：** 固定版本和名称映射；历史记录漂移直接拒绝启动；后续只能追加版本。
- **SQLite DDL 或数据修复部分落盘：** 继续由单一 `engine.begin()` 包裹，使用失败注入测试验证回滚。
- **已有 KmAI 标记重复执行：** 引导阶段接纳并映射旧记录，版本 5 不再执行。
- **重复工序阻塞唯一索引：** 启动只建立普通索引并记录迁移结果；显式备份修复后再升级唯一索引。
- **备份遗漏 WAL 内容：** 使用 SQLite 在线备份 API，不使用数据库主文件的直接复制作为备份机制。
- **维护期间并发写入：** 文档要求停止 API；命令设置超时并在事务中重新扫描、修复和验证。
