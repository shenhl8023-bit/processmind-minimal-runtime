# 第二步归并模型辅助与交互反馈设计

## 目标

让第二步中间归并能利用大模型给出基于来源证据的候选建议，同时保持规则校验和用户审核对最终结果的控制；右侧标准路线继续由审核状态确定性生成。另行修复单条归并操作在状态缺失或请求失败时缺少明确反馈的问题。

## 当前行为

- 左侧全集工序树的构建和排序已有独立流程，本设计不改动第一步。
- `build_initial_merge_groups()` 根据本地归并规则产生中间候选，`merge_route` 提示词目前没有调用方。
- 工作台快照基于候选组、建议及审核状态构建右侧标准路线。
- 前端归并动作在无法找到当前候选组或后端建议时会静默返回 `false`；接口异常会显示错误，但调用方对返回值的处理可能仍需核对。

## 方案

### 模型职责

在现有规则候选生成后调用归并判断提示词。模型只能对系统提供的候选组给出建议，不得创建候选、删除来源工序或直接改变已审核状态。建议至少包含候选 ID、动作（直接归并、并入上位工序、保持独立）、建议名称、理由和来源证据引用。

模型输入使用候选涉及的来源工序、工步摘要、前后顺序和样本覆盖信息；仅提供完成判断所需的证据，避免把整个项目无边界地送入提示词。输出使用固定 JSON 结构。服务端校验候选 ID、动作枚举、来源覆盖、重复引用和名称非空；非法、超时、未配置模型或调用失败时，沿用现有规则建议并记录可诊断原因。

本阶段模型输出作为“系统建议”展示。用户通过现有确认/不合并/改名动作审核后才更新状态。模型不自动确认，也不覆盖人工审核。

### 右侧标准路线

右侧继续由中间归并组和审核状态确定性投影生成，不增加第二个自由生成路线的模型调用。排序保留原始来源顺序及当前终段放行规则；同编号但不同来源/阶段的工序不因编号相同而强行合并。人工确认后的结果应可追溯到来源组和审核动作。

### 提示词

将未接入的通用 `merge_route` 提示词改为面向候选组的归并判断提示词，或明确拆成独立模板。提示词要求模型：

- 只输出 JSON，且只能引用输入中的候选 ID 和证据项 ID。
- 区分语义等价、上位包含和名称相似但工艺意图不同三类关系。
- 结合加工对象、工艺方法、精度/作用、工步证据、来源顺序和阶段判断；设备差异本身不能作为拆分或合并的充分依据。
- 保留不同阶段的重复工序，以及编号相同但语义/来源不同的工序；证据不足时选择保持独立。
- 对每个候选给出简短理由、可核对的证据引用和置信等级；不臆造输入之外的事实。

提示词不负责决定路线序号或直接操作数据库。服务端校验与人工审核构成决策边界。

### 点击无反馈

确认和不合并动作在缺少候选组、建议 ID、项目 ID、工作区刷新失败、接口错误或工作流版本冲突时，都应设置可见错误或状态提示。成功后只有在刷新成功时才报告工作区已更新；批量操作在首个失败时停止并保留失败信息，不显示“全部完成”。

## 版本与回退

归并提示词版本、决策算法版本及来源签名需要能识别旧快照并触发重建，避免旧规则建议与新模型建议混用。模型不可用或返回无法通过校验的结果时，工作台仍可由现有规则正常使用。模型调用应使用现有 LLM 配置和客户端，不另加服务商依赖。

## 验收标准

1. 单条确认、不合并和改名在有效建议上仍可使用；无效状态、后端错误和版本冲突均向用户显示明确反馈。
2. 归并提示词在工作台构建时实际被调用，模型只能影响未审核候选的建议字段。
3. 模型输出非法、超时或模型未配置时，工作台回退到现有规则建议，且右侧路线仍可生成。
4. 已审核动作不会被快照重建或模型返回覆盖。
5. 右侧路线只根据归并/审核状态生成；相同序号的不同工序不被误当作同一个节点，来源明确的末段包装/放行顺序得以保留。
6. 后端测试覆盖模型输出校验、失败回退、审核保护和快照版本变化；前端测试覆盖无反馈分支和批量首错反馈。

## 不在本次范围

- 改写第一步 PDF 提取、左侧树生成或排序。
- 让模型自由生成、排序或直接保存右侧标准路线。
- 自动接受模型归并建议，或改变已审核的人工决定。
- 改造工作台以外的提示词、规则包或工艺分析流程。
