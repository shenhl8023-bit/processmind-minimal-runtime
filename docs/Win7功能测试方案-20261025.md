# ProcessMind Win7 功能测试方案

更新日期：2026-10-26。测试对象：`processmind-win7-windows-20261026-fix5.zip`，版本 `1.0.1+20261026-fix5`。fix4 存在 Python 3.13 运行时误入包的问题，已停止用于 Win7 验收；详见缺陷清单 BUG-006。

本方案用于下一轮执行。下方业务用例均尚未在新包的 Win7 实机上执行，不能据此标记为通过。

## 1. 推荐的测试方式

建议采用“自动化回归 + Win7 业务验收 + 异常操作测试”。

| 方式 | 能发现什么 | 局限 |
| --- | --- | --- |
| 只人工点击页面 | 页面问题、工艺结果不合理、使用不顺畅 | 容易漏掉刷新、重启、重复操作；每次改动都要重测 |
| 只运行现有自动化测试 | 逻辑回归、接口参数、数据版本和状态处理错误 | 不能证明 Win7 实际可用，也不能代替工艺人员判断结果 |
| 三种方式结合（推荐） | 同时检查代码逻辑、实际安装包和跨步骤状态 | 需要先准备一套有人工预期结果的小样本 |

先执行第 4 节的 12 项关键用例；通过后，再按第 5 节扩展。后续每修一个缺陷，就把它的复现步骤加入自动化或固定人工回归清单。

## 2. 先准备一个可以判定对错的测试环境

1. 在旧包目录运行 `stop-win7.cmd`，停止旧服务。新启动器会复用已有的健康服务，因此旧服务未停时，可能仍在测试旧代码。
2. 服务停止后备份整个 `%LOCALAPPDATA%\ProcessMind` 目录；如果配置过自定义运行目录，备份实际目录。
3. 把新 ZIP 解压到新目录，避免覆盖旧包。已安装 KB2533623 或包含它的后续更新时，无需重复安装。
4. 记录 Win7 SP1 x64、浏览器名称及完整版本；基线为 Chrome 109 或 Edge 109。
5. 推荐给这一轮测试使用独立运行目录。在新包目录打开同一个 CMD 窗口，依次执行：

```bat
set "PROCESSMIND_RUNTIME_DIR=%LOCALAPPDATA%\ProcessMind-Test-20261025"
call start-win7.bat
```

以后在**这个 CMD 窗口**运行 `call status-win7.cmd` 和 `call stop-win7.cmd`。这个窗口保留了测试运行目录设置；另外双击停止脚本会使用默认目录，可能无法停止测试服务。测试目录首次启动没有项目和模型配置，需要单独配置。

若直接使用默认运行目录，则至少新建“Win7-20261025-测试A”和“Win7-20261025-测试B”两个任务。所有删除、重置、失败注入只对测试任务执行。

### 小样本及人工答案

使用你已经核对过的 3～5 份规程和 1 份 XML 分组模板。不要一开始就用几十份资料，否则很难判断是抽取错误、合并错误还是模型差异。

在纸上或表格里先写清：每份规程的工序顺序、每道工序的工步、应该合并的工序、必须独立的工序、模板映射，以及至少 3 组输入条件对应的正确生成结果。判定依据以原始规程和工艺人员确认结果为准。

专门准备或选择以下情况：

- “车外圆B”含多个工步，另有一道可以参与合并的工序，例如“铣扁”。
- 同名工序出现在不同阶段；不同工序下存在同名工步。
- 模板至少包含 3 个需要映射的分组，便于测试“先保存一部分，再补齐”。
- 条件样本包含规则命中、不命中和阈值边界。

## 3. 每个保存动作都做四种复查

这是本系统最值得重点测试的部分，不能只看“保存成功”提示。

1. **当前页面**：数量、名称、关联关系和版本是否正确。
2. **刷新或前后切换步骤**：重新读取的数据是否仍然正确。
3. **关闭浏览器，再次打开**：已保存结果是否保留，服务能否复用。
4. **停止服务，再次启动**：已保存结果是否保留，后续步骤是否读取到了新状态。

涉及任务的数据，还要在 A、B 两个任务之间切换一次。未保存的内容单独观察草稿或离开提示，不把“未保存内容仍然存在”当成必然要求。

### 合并拆分的具体判定例子

如果合并前是：

```text
车外圆B
  车端面、车外圆、镗孔、车槽、攻螺纹
铣扁
  铣扁
```

那么拆开后应恢复为 2 道工序，工步分别为 5 个和 1 个。不能变成 6 道工序，也不能把 6 个工步全塞回其中一道工序。

比较工步时要看“属于哪一道来源工序”，不能仅按工步文字去重，因为不同工序可能合法地包含同名工步。若先手工改过合并结果名称，另外记录拆分时名称恢复规则是否符合业务预期。

## 6. 执行顺序与通过条件

1. **第一轮**：执行 C01～C12，先找阻断主流程、丢数据、串任务、错误生成的缺陷。
2. **第二轮**：执行 U、R、A、M、F、G、K 用例，并用工艺人员的答案核对内容。
3. **第三轮**：执行 N、W、H 用例，重点测试失败后的恢复和不同操作顺序。
4. **修复后**：原始复现步骤重测一次，再测相邻步骤和保存/重启；加入后续回归清单。

主流程不通、数据丢失、跨任务污染或规则生成错误，应作为本轮验收阻断。错误提示、界面和边界问题单独登记，不以“没有崩溃”判断通过。最终结论写清“已通过哪些场景、失败哪些场景、哪些尚未覆盖”。
