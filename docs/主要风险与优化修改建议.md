# ProcessMind 主要风险与优化修改建议

> 分析日期：2026-08-12  
> 目的：只记录当前代码中需要优先优化或修改的主要风险。  
> 范围：后端任务执行、规则包生命周期、前后端契约、安全、数据库和交付质量。  
> 说明：除“已通过验证”的项目外，本文风险均表示需要治理的工程风险，不等同于已经在线复现的故障。

## 1. 总体判断

当前项目的核心业务链路已经可用，后端全量测试、前端测试、契约检查和构建均已通过。但代码更偏向“本地单进程桌面应用”的可靠性假设，若直接按多 worker、内网多人或长期生产服务运行，以下问题会逐步暴露：

1. 后台提取任务的真实执行状态依赖进程内存。
2. 规则推导逻辑在前端和后端存在重复实现。
3. 规则包状态聚合是关键闸门，但测试覆盖明显不足。
4. 缺少真实浏览器端到端闭环测试。
5. 设置接口和密钥存储不适合未经防护的内网部署。
6. SQLite、JSON Text 字段和字符串状态对数据一致性的保障有限。
7. 大型页面和服务文件提高后续修改的回归成本。

## 2. 风险优先级

| 优先级 | 风险 | 当前判断 | 建议 |
|---|---|---|---|
| P0 | 多 worker 下提取任务状态不可靠 | 架构风险，已有代码证据 | 立即明确单 worker；随后增加数据库 lease |
| P1 | 规则语义前后端重复实现 | 高概率产生漂移 | 后端成为发布语义唯一来源 |
| P1 | 规则包状态测试不足 | 已有覆盖率证据 | 建立状态矩阵和失效场景测试 |
| P1 | 缺少真实 UI 闭环测试 | 交付风险 | 增加 Playwright 最小流程 |
| P2 | 设置接口存在 SSRF/未授权风险 | 本机部署风险较低，内网部署风险高 | 增加认证、地址白名单和网络限制 |
| P2 | API Key 明文文件存储 | 输出已脱敏，但磁盘仍敏感 | 改用环境变量或系统凭据存储 |
| P2 | 数据库约束不足 | 目前依赖业务代码 | 增加约束、统一 JSON 边界和数据审计 |
| P3 | 大型模块维护成本高 | 已由代码规模证实 | 渐进拆分，不做一次性重构 |

## 3. P0：提取任务的多进程可靠性

### 3.1 现状与证据

提取任务在 [extraction_tasks.py](../process-plan-agent-api/app/services/extraction_tasks.py) 中维护以下进程内结构：

- `EXTRACTION_TASKS`
- `EXTRACTION_RUNNING`
- `EXTRACTION_JOBS`
- `EXTRACTION_QUEUE_LOCKS`

任务由 [extraction_pipeline.py](../process-plan-agent-api/app/services/extraction_pipeline.py) 使用 `asyncio.create_task()` 启动。数据库虽然保存了 `extraction_task_states`，但实际的 `asyncio.Task`、运行集合和项目锁只存在当前进程。

### 3.2 影响

- API 使用多个 worker 时，worker B 看不到 worker A 的 `asyncio.Task`。
- worker 重启后，数据库可能仍显示 `running`，但原任务已经不存在。
- 两个进程可能分别认为自己可以处理同一项目。
- 超时回收逻辑可能把仍在另一进程运行的任务标记为失败。
- LLM 调用和数据库清理都可能发生重复执行。

### 3.3 建议修改

**短期必须修改：**（第 1 步已落实，见“第 3 步进度”）

1. 在 Windows 启动脚本、Docker 命令和部署文档中明确 `single worker` 运行约束。
2. 在启动时输出当前 worker 模式，避免部署人员误以为可以横向扩展。
3. 将任务状态中的“本进程正在执行”和“数据库租约有效”分开显示。

**中期建议：**

为 `extraction_task_states` 增加：

```text
owner_id
lease_expires_at
heartbeat_at
attempt
```

任务启动时用条件更新抢占租约；执行期间定时续租；完成和失败时必须带 `owner_id` 条件更新。租约过期后才允许其他 worker 接管。

> **第 1 步进度（2026-08-12）**：单 worker 约束已在全部正式启动路径显式声明（`--workers 1`），启动时输出当前 worker 模式，并在任一 worker 环境变量显式配置多 worker 时拒绝启动（见 `app/services/worker_mode.py`，根接口 `/` 返回 `single_worker_declared`）。租约字段 `owner_id / lease_expires_at / heartbeat_at / attempt` 已加入模型与迁移 v6，并接入任务启动（原子条件抢占 `claim_task_lease`）、执行期间续租（后台心跳，过期租约不可复活）、完成/失败（带 owner 条件终态写入，被接管时回滚业务结果与项目状态）与状态解析（分别返回 `local_execution_active` / `lease_valid`）。竞态与崩溃恢复测试见 `tests/test_extraction_task_lease.py`，覆盖双会话及双进程抢占、进程崩溃后接管、旧 owner fencing、无任务行恢复竞态、快捷完成竞态和终态事务回滚；启动约束测试见 `tests/test_worker_mode.py`。

### 3.4 验收标准

- 两个独立进程同时启动同一项目，只有一个获得任务租约。
- 持有租约的进程崩溃后，任务在租约过期后可被接管。
- 旧 owner 在恢复后不能覆盖新 owner 的状态。
- 重启 API 后，任务状态不会永久停留在 `running`。
- 至少有双进程竞态、租约过期和任务恢复测试。

## 4. P1：规则语义在前后端重复实现

### 4.1 现状与证据

前端 [finalizeRulePackage.ts](../process-plan-agent-ui/src/utils/finalizeRulePackage.ts) 包含：

- 主线/条件/关系规则判断。
- 条件文本启发式判断。
- 默认 V2 测试用例生成。
- 条件树归一化。
- 自定义条件值补充。

后端同时在 `condition_parser.py`、`condition_review_service.py`、`validator.py`、`compiler.py` 和 `planner.py` 实现同一业务链路的解析、绑定、校验和执行。

### 4.2 影响

- 页面显示“可发布”，后端仍可能判定不可发布。
- 前端默认测试用例和后端执行结果不一致。
- 修复规则时需要同时修改 TypeScript 和 Python。
- 用户看到的条件解释可能不是最终发布的条件 AST。

### 4.3 建议修改

1. 后端负责生成最终规范化条件树、默认测试用例和 V2 package payload。
2. 前端只保留交互辅助判断，不把启发式判断作为发布依据。
3. 发布接口重新执行完整解析、绑定、验证和测试，不信任前端传入的派生结论。
4. 建立共享 golden fixtures：同一输入分别经过前端展示辅助和后端发布校验，结果必须满足明确契约。
5. 在 API 响应中返回标准化后的规则和验证路径，让前端直接展示后端结果。

### 4.4 验收标准

- 相同规则输入在前端预览、后端验证和最终 ZIP 中的条件结构一致。
- 前端删除或改变启发式分类函数后，发布行为不改变。
- 每个主要规则类型至少有一个跨前后端 fixture。
- 发布接口在前端伪造 `valid=true` 或测试结果时仍能正确拒绝无效规则。

## 5. P1：规则包状态聚合测试不足

### 5.1 现状与证据

[status.py](../process-plan-agent-api/app/services/rule_packages/status.py) 统一计算：

- `can_publish`
- `can_generate`
- `package_executable`
- blocker 列表
- 审核统计
- KmAI 兼容性统计

当前规则包整体覆盖率为 `86.54%`，但该文件此前统计覆盖率约为 `35%`，显著低于整体门槛。

### 5.2 影响

状态聚合一旦判断错误，会直接导致：

- 未完成审核的包被发布。
- 已失效或来源已变更的包仍可生成路线。
- KmAI 不兼容的包被当作可执行包。
- 前端按钮状态与后端真正能力不一致。

### 5.3 建议修改

建立状态矩阵测试，至少覆盖：

1. 项目不存在。
2. 项目未完成路线提取。
3. 没有规范化路线。
4. 有待确认规则。
5. 存在无效标准因子绑定。
6. 没有已发布包。
7. 发布包关联路线已变化。
8. 已确认规则来源已变化。
9. 发布包 JSON 无法解析。
10. V2 校验失败。
11. KmAI 兼容性失败。
12. 所有条件满足时发布和生成均可用。

### 5.4 验收标准

- 每个 blocker code 都有正向和反向测试。
- `can_publish`、`can_generate` 和 `package_executable` 的组合关系有明确断言。
- 状态 API 的 OpenAPI 响应 fixture 与前端 DTO 同步验证。
- 状态聚合文件覆盖率达到 85% 以上，且不是通过排除代码实现。

## 6. P1：缺少真实浏览器端到端闭环

### 6.1 现状与证据

当前 CI 已运行后端 pytest、前端 Vitest、API 契约检查和生产构建，但没有把以下真实流程作为持续门禁：

```text
创建项目 -> 上传文件 -> 启动提取 -> 查看任务状态
-> 路线归并 -> 条件确认 -> 发布规则包 -> 输入因素 -> 生成路线
```

### 6.2 影响

单元测试和构建通过，仍可能存在：

- 路由跳转丢失 `project_id`。
- 页面缓存显示旧的路线或旧的规则包。
- 409 workflow revision 冲突未正确提示。
- 下载 ZIP 的 Content-Disposition 或文件内容错误。
- 前端按钮状态与真实 API 状态不一致。

### 6.3 建议修改

增加最小 Playwright 流程，使用测试数据库和可控的 LLM stub，至少覆盖：

1. 创建项目并上传一个合法文件。
2. 模拟提取成功，确认任务状态和路线显示。
3. 修改一条规则并确认保存。
4. 发布规则包并检查状态。
5. 提交因素并生成路线。
6. 模拟旧页面提交，确认 409 冲突提示和刷新行为。
7. 修改来源资料，确认旧规则包失效。

### 6.4 验收标准

- CI 可在无外部 LLM Key 的情况下稳定执行。
- 每次流程失败能定位到页面、请求和响应状态。
- 至少保存关键步骤截图或 trace，失败时上传为 CI artifact。
- 测试不会读写开发环境真实 `data/`。

## 7. P2：设置接口的 SSRF 和未授权风险

### 7.1 现状与证据

[settings.py](../process-plan-agent-api/app/routers/settings.py) 提供：

- `/api/settings/test-connection`
- `/api/settings/models`

接口会根据请求或配置中的 URL 发起 HTTP 请求。当前应用默认面向本机使用，Docker Web 也默认只绑定 `127.0.0.1`，因此当前风险受部署边界限制。

### 7.2 影响

若服务暴露到内网或被反向代理公开，攻击者可能让服务请求：

- 云平台 metadata 地址。
- 内网管理接口。
- 本机其他服务。
- 需要从服务器网络访问的受保护地址。

此外，若没有认证，任何能访问 API 的用户都可能修改模型配置或触发外部请求。

### 7.3 建议修改

1. 增加可选认证开关，内网部署默认要求认证。
2. 只允许 `https`，本地开发可显式允许 `http://127.0.0.1`。
3. 对 hostname 解析后的 IP 拦截 loopback、link-local、私有网段和 metadata 地址。
4. 允许配置 provider 白名单，而不是接受任意 URL。
5. 为连接测试设置更短超时、响应体大小限制和审计日志。
6. 将“保存配置”和“测试连接”权限分开。

### 7.4 验收标准

- 请求私有 IP、重定向到私有 IP、非 HTTPS 地址时被拒绝。
- 配置接口没有认证时不能在非本机部署模式下启用。
- API Key、请求 URL 和响应正文不会写入普通日志。

## 8. P2：API Key 明文文件存储

### 8.1 现状与证据

[settings_store.py](../process-plan-agent-api/app/services/settings_store.py) 通过临时文件和 `os.replace` 原子写入配置，但 `LLM_API_KEY` 和 `KNOWLEDGE_SEARCH_API_KEY` 最终仍保存在 JSON 文件中。API 响应会脱敏，这是正确的，但不能解决磁盘泄露问题。

### 8.2 建议修改

优先级从低到高：

1. 本地版：启动时检查配置文件权限，文档明确该文件是敏感文件。
2. Windows：使用 DPAPI 或 Windows Credential Manager。
3. Docker/服务器：使用环境变量、Secret mount 或外部 secret manager。
4. JSON 文件只保存非敏感配置，敏感字段保存引用名。
5. 提供密钥轮换和清除接口，并保证日志不打印密钥。

### 8.3 验收标准

- 打包脚本不会包含真实密钥。
- 备份、异常和审计日志不会出现完整 API Key。
- 读取配置失败时错误信息不包含密钥内容。
- 密钥被清除后，旧值不会继续被 LLM 客户端读取。

## 9. P2：SQLite 和数据库约束不足

### 9.1 现状与证据

当前数据库明确只支持 SQLite。模型中大量字段使用字符串状态和 `Text` JSON，例如规则包内容、条件审核内容和生成结果；多个外键也允许为空。数据库迁移已经有唯一索引和部分外键，但业务有效性主要仍由 Python 服务保证。

### 9.2 影响

- 手工或异常写入可能产生未知状态值。
- JSON 损坏只能在读取或发布时发现。
- 数据库迁移后历史数据可能满足旧约束但不满足新规则。
- 删除和级联关系复杂，容易出现孤儿文件或孤儿记录。

### 9.3 建议修改

1. 对项目、任务、规则包和审核状态增加 CHECK 约束。
2. 对核心外键明确 `ON DELETE` 策略，避免各路由手写级联删除。
3. 为 JSON Text 字段建立统一 repository/serializer，不在各处直接 `json.loads`。
4. 启动维护命令增加 JSON 完整性、孤儿记录和文件一致性审计。
5. 为迁移增加“旧数据审计 -> 修复 -> 新约束”的分阶段迁移。

### 9.4 验收标准

- 非法状态无法通过数据库写入。
- 所有规则包 JSON 在发布和启动审计时都可解析。
- 删除项目后不存在关联孤儿记录和上传文件。
- 每个迁移都有回滚/失败恢复测试或明确不可逆说明。

## 10. P3：大型模块导致维护和回归成本上升

### 10.1 现状与证据

当前较大的文件包括：

- `ExtractView.vue` 约 1618 行。
- `FinalizeView.vue` 约 1594 行。
- `AnalysisView.vue` 约 1411 行。
- `param_audit.py` 约 928 行。
- `db_schema_migrations.py` 约 820 行。

这不表示文件本身一定错误，但说明一个页面或服务同时承担了较多状态协调、业务判断、序列化和展示职责。

### 10.2 建议修改

按职责渐进拆分：

1. 页面只保留布局和事件编排。
2. 请求加载、刷新、竞态控制单独放入 workspace composable。
3. 纯规则判断放入无副作用模块，并由后端结果校正。
4. 数据转换和 API DTO 单独维护。
5. 参数审计按查询、问题生成、答案持久化、路线构建拆分。
6. 数据库迁移保持单迁移单职责，并补充迁移审计工具。

### 10.3 验收标准

- 新增业务规则不需要同时修改多个页面的大段脚本。
- 纯函数可以脱离 Vue 或数据库单独测试。
- 页面测试重点覆盖交互，规则测试集中在服务层。
- 拆分过程中不改变 API 和规则包协议。

## 11. 推荐实施顺序

```text
第 1 步  ✅ 明确单 worker 约束，并补提取任务竞态/重启测试（已完成）
第 2 步  补规则包状态矩阵测试
第 3 步  将发布语义收敛到后端，建立前后端 golden fixtures
第 4 步  增加 Playwright 上传到生成闭环
第 5 步  增加设置接口认证、SSRF 防护和密钥存储改造
第 6 步  增强数据库约束与运行数据审计
第 7 步  渐进拆分大型页面和服务文件
```
